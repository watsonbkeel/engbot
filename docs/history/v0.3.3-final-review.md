## 2. 提示词与实际对话预算

`prompts/scenes.md` 的生成规则明确保留双方角色、学生的目标以及提问主导权；机器人可以作为顾客、访客或受访者回答。对话输出不再强制每句附带问题，仅当角色与尚未完成的步骤需要时增加至多一个问题或指令。核心目标要求在六次简短学生交流内可完成，高难度的额外细节属于可选内容。

`Tutor.dialogue()` 使用同一个 `dialog_limit()` 计算预算和结束上限，并发送：

- `total_turns`：配置场景为 basic 6、standard 8、challenge 10；无配置场景的兼容对话为 4、6、8。
- `completed_turns`：开场完成后的首次机器人发言为 0；正常答复包含当前学生这一轮。
- `remaining_turns`：上限减去已完成数，最低为 0。
- `closing`：只在有当前学生答复且已到实际上限时为 true。

实际回归验证了三种场景上限、三种兼容对话上限，以及解释、表达帮助、示范跟读、重播、未听清不消耗普通对话轮数。新字段供配置场景提示词安排节奏；没有借此改变旧兼容对话的固定上限。

上述审查证明规则和实际预算送达模型。是否每次都保留合适角色、作出准确的语言反馈，属于模型语义表现，不能由提示词静态检查或这些测试替身证明。真实 GPT 实录的教学评估由本轮单独的模拟报告承担。

## 3. 自然结束与学习证据

新增 `scene_complete` 是模型输出中的可选字段。缺省为 false；若显式存在，只接受 JSON 布尔值，字符串、数字、null 和数组均被拒绝。校验在历史追加、词汇写入和轮数增加之前执行，格式错误不会被当作完成。

引擎只在同时满足以下条件时接受提前结束：配置了 scene、存在当前学生答复、至少已发生两轮学生对话、`relevant` 严格为 true、`scene_complete` 严格为 true。首次角色回应、第一轮学生答复、无配置场景的通用对话、`relevant=false` 的矛盾输出均不能用该信号提前结束。旧模型完全不返回该字段时仍按原上限收尾。

审查员核对了最后加入的相关性保护，以及 `test_contradictory_irrelevant_answer_cannot_trigger_natural_completion` 的实际通过结果。这里不声称独立重跑了该修复的红测阶段；本次独立验证的是最终代码和通过输出。

### 最后一句与学习记录的顺序

实际顺序是：解析并保留角色回复及当前历史 → 按原有逐词证据规则写入实际出现的目标词 → 更新本轮观察 → 增加对话轮数 → 判断自然结束或上限 → 生成点评 → 追加结束语。

因此 `scene_complete` 不绕过逐词判断，也不为未出现的词制造记录。原有“明确正确、独立、未复制、未受助”等掌握条件保持原样。结束标记本身没有数据库写入路径。新回归中的“无目标词自然告别”保持零词汇写入；结束成功并不等于所有目标词已掌握。

审查员补充运行了一个相反方向的探针：第二轮学生说出带 apple 的独立正确表达并告别，模型返回自然结束。结果在第 2 轮变为 done，apple 的真实证据正常写入一次；点评 user JSON 保留该最后一句和对应独立观察，输出第一个片段仍是最后的角色回复。提前结束既没有凭空加分，也没有丢弃本来有效的最后一轮证据。

## 7. 追加审查：可选 thinking 参数兼容

本节审查在上文场景审查完成后追加的 `english_class/providers.py` 差异、`tests/test_llm_optional_thinking.py` 及设置页说明。修复目标是：保留第一条请求的显式 thinking 偏好；仅在明确拒绝整个可选字段、且原偏好为 disabled 时，去掉这个字段重试一次。开启推理遇到同类拒绝应明确报错，不能默默关闭；其他字段、值错误或状态码不触发本项兼容重试。

相关协议说明与初始问题证据见 `llm-optional-thinking.md`。本次独立审查没有用真实账号观察任何供应商的 HTTP 400；下面所有响应均是明确的测试数据。

### F033-1 · Important · 消息前缀误认子字段或值错误（已关闭）

**位置：** `_unsupported_thinking_parameter()` 的 message 兜底匹配，以及 `Providers.chat()` 的去字段重试分支。

**独立复现：** 初版使用前缀匹配，把点号和空白当成 thinking 字段结束。因此下面的 HTTP 400 被认作拒绝整个 thinking 字段：

```json
{"error":{"message":"Unsupported parameter: thinking.type","param":null,"code":null}}
```

审查员调用实际 `Providers.chat()`，仅替代 DNS 和外部 HTTP：第一条请求含 `thinking: {"type":"disabled"}`，第二条已经删去 thinking，随后返回成功。检查函数也错误接受 `Unknown parameter: 'thinking.budget'` 和 `Unsupported parameter: 'thinking' value is disabled`。

**影响：** 子字段或具体值不被接受，并不能证明顶层 thinking 不被支持。删去整个字段会绕过本来应显示的配置错误；如果该端点省略字段时默认开启推理，还可能改变用户关闭开关的实际效果。故不能把此情况作为普通宽松兼容保留。

审查员立即把复现交给实现者，没有自行修改生产代码或测试。在实现者先加入三个负向回归、尚未修复匹配器的阶段，审查员独立运行获得 **3 failed, 20 passed in 0.40s**；三个用例均因本应抛错却返回成功而失败。

**最终修复：** 对缺少明确字段元数据的 message 分支使用完整字符串匹配，字段必须恰好为 thinking，允许成对的可选引号及末尾句号/感叹号；不再允许子字段、值错误后缀或不成对引号。明确的 `param="thinking"` 加 `unsupported_parameter/unknown_parameter/unrecognized_parameter` 元数据仍能识别，不要求这类错误的 message 完全符合短句模板。`unsupported_value`、`invalid_value`、`invalid_parameter` 等代码继续直接排除。

实现者同时补上不成对引号负例和带引号的合法消息正例。审查员读取最终实现，再独立运行：


结果为 **25 passed in 0.45s，退出码 0**。包括原始兼容路径、三个误匹配复现、引号边界、明确开启时不移除、其他错误不重试、重试上限、共享截止时间，以及实际公共 API 的保存/生成/保存失败保留旧配置。**F033-1 关闭。**

### 重试的网络、凭证和时间边界

独立代码核对及实际执行确认：

| 边界 | 最终行为与证据 |
|---|---|
| 第一次请求 | 仍显式发送 enabled / disabled；接受该字段时只有原请求，没有兼容重试 |
| 触发条件 | HTTP 400、结构化 error、明确拒绝顶层 thinking，且原值为 disabled；其他参数、值错误、子字段、一般 400、401/403/404/429/500 均不因正文提及 thinking 而重试 |
| 删除范围 | 新正文只删 thinking；messages、model、JSON 输出要求、temperature、max_tokens 等其他内容保持 |
| 启用偏好 | enabled 遇到字段拒绝抛出 `UnsupportedThinking`，提示关闭开关或换模型；保存探针返回 422，旧配置完整保留 |
| 请求次数 | 兼容重试最多一次；第二次响应不再进入同一兼容判断，不形成循环 |
| DNS 与目的地 | 兼容请求沿用产生明确 400 的同一已验证目标，不重新解析，不切换到其他学生或模型供应商 |
| 密钥与 TLS | 沿用同一 Authorization、Host、TLS SNI 与客户端；没有跳过证书检查，也没有把学生 Key 放入请求正文 |
| 代理与重定向 | 学生模型继续 `trust_env=False`、`follow_redirects=False`；重试返回重定向时正常失败 |
| 截止时间 | 第二次请求位于原 `asyncio.timeout` 内；回归以两次各 0.06 秒、总限时 0.1 秒验证总限时没有翻倍 |

初始连接失败时仍允许原有的“尝试另一个已验证 IP”行为，这与新增的一次可选字段重试是不同的步骤。审查员另运行两个临时传输探针：第一个 IP 抛出 ConnectError，第二个已验证 IP 返回明确 thinking 字段拒绝；兼容请求仍发往第二个 IP，保留原 Host、SNI 和凭证。随后把兼容响应改为指向本机的 302，实际客户端拒绝该响应，没有向重定向地址发请求，也没有第四次请求。两个探针均通过；所有连接都由 MockTransport 处理，没有访问这些测试地址。

设置页新增说明清楚指出：不支持 thinking 扩展的模型，在关闭开关并移除字段后按供应商默认方式运行；不承诺其他厂商自身的推理能力或速度也被这个开关关闭。适配器没有把该字段映射为其他厂商的专有推理参数。
