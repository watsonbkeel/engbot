# 树莓派＋云台＋摄像头跨项目接入说明

版本：v1.0｜编制日期：2026年10月21日｜面向：项目开发者与接手开发的 AI 助手

**核心结论：优先保留树莓派上的独立硬件服务，由新项目通过 HTTP 调用。不要让新项目与现有服务同时占用串口或摄像头。**

本文依据2026年10月20日已部署、实测且经 Watson 目视验收的版本编写。最后一次在线配置核验为10月20日22:43；10月21日编写期间 SSH 连接超时，未重新确认设备当前在线状态。下文“现有”均指这一已验证基线，不代表已完成新项目整合。

## 1. 接手者先读：能做什么、不要做什么

### 1.1 已具备的能力

| 能力 | 实现与接口 | 当前边界 |
|---|---|---|
| 实时看画面 | 网页、MJPEG `/video_feed` | 640×480，配置目标20帧/秒，未做长期性能测试 |
| 获取单帧 | JPEG `/snapshot.jpg` | 返回内存中的最新帧，不保存照片文件 |
| 云台方向微调 | `/step` | 基于舵机实测角度计算相对移动 |
| 指定目标角度 | `/move` | 角度范围校验；普通单次移动限制约30° |
| 读取真实位置 | `/position` | 使用 `T1001.pan/tilt`，不使用 IMU 代替 |
| 保存自定义中位 | `/home/save` | 需明确确认；稳定实测位置写入本地文件 |
| 回到保存的中位 | `/center` | 无中位时拒绝，不默认回硬件零点 |
| 健康检查 | `/health` | 同时检查摄像头画面与舵机反馈新鲜度 |
| 开机启动 | `pantilt-web.service` | 已启用；应用启动不主动移动云台 |

当前没有录像、录音、RTSP、WebRTC、目标跟踪、人脸识别、云台自动巡航或 HTTP 急停接口。不要把上述能力写成已有功能。LED 控制在此前测试中未观察到生效，不列入可复用能力。

### 1.2 四条不可破坏的约定

1. **一个硬件所有者。** 现有服务独占 `/dev/serial0` 和摄像头；其他项目通过接口调用。不得同时启动旧官方上位机或串口测试脚本争用设备。
2. **启动不转动。** 载入中位只用于后续归中，不能在开机、刷新页面、重连或健康检查时自动执行移动。
3. **中位是用户认可的视角，不是硬件零点。** 不得为了“归中”重新校准舵机 EEPROM，也不得擅自改舵机 ID。
4. **以实测确认结果。** 写串口成功、HTTP 200、IMU 数据存在，都不等于用户认可的方向正确；必须检查实测反馈，并保留目视验收。

## 2. 硬件与网络基线

### 2.1 当前设备

| 项目 | 已验证配置 |
|---|---|
| 主机 | 树莓派4B，Linux；运行用户 `chs` |
| 云台 | Waveshare 2-Axis Pan-Tilt Camera Module，ESP32控制板＋两轴总线舵机 |
| 摄像头 | CSI 摄像头，Picamera2 识别型号 `ov5647` |
| 控制链路 | 树莓派 GPIO UART → ESP32 → 舵机总线；不是直接输出 PWM |
| 上位串口 | `/dev/serial0`，当时指向 `/dev/ttyAMA0` |
| 串口参数 | 115200，8N1；UTF-8 JSON，一条命令一行，以换行结束 |
| 轴寻址 | 水平 ID 2、俯仰 ID 1；已验证 ID 11 无响应 |
| 供电 | 控制板与舵机有独立外部电源；此前使用12V供电 |
| 当前软件中位 | X=−55°，Y=4°，2026年10月20日经用户确认 |

电压、极性、电流和接线端子须以设备铭牌及官方说明为准。USB 灯亮不代表舵机外部电源就绪；当前正式控制链路是 GPIO UART，不依赖 USB 控制线。

### 2.2 连接参考与复用注意

下表是标准 UART 连接参考，不是本次重新测量过的逐针接线照片。接手者应先核对控制板端口丝印和当前实物，不要盲插。

| 树莓派端 | 连接方向 | 控制板端 |
|---|---|---|
| BCM14 / TXD，物理针8 | 输出 → 输入 | RX |
| BCM15 / RXD，物理针10 | 输入 ← 输出 | TX |
| GND，例如物理针6 | 共地 | GND |
| CSI 接口 | 摄像头排线 | 摄像头模块 |

UART 使用3.3V逻辑电平；不要把舵机电源接到树莓派 GPIO。排线及供电接线调整前先断电。新设备须启用硬件串口、关闭串口登录控制台，并核对 `/dev/serial0`；当前树莓派已完成这些配置，迁入新项目不需要重复折腾硬件。

### 2.3 访问地址与断网回退

- 固定接入地址：`http://100.73.202.93:5000`，仅绑定该 Tailscale 地址；访问端需要具备 Tailnet 可达性和相应权限。
- 10月20日局域网地址：有线 `192.168.3.138`、无线 `192.168.3.26`，均可能变化。服务没有绑定这些地址，不能假定局域网 IP 加5000端口同样可访问。
- 有线默认路由 metric=100；三组 WiFi metric=600，自动连接优先级为：跟我练AI创造100、Bkeel50、TP-LINK_0645为10。
- 控制板 `PT` 热点保留但禁止自动连接、禁止默认路由及自动DNS。GPIO 控制不要求树莓派连接 PT 热点。
- 自动连接优先级用于连接或重连时选网，不保证连接正常时主动切换到更高优先级，也不是“WiFi关联仍正常但互联网异常”时的跨热点探测机制。

已验证临时断开有线后 TP-LINK_0645 能独立维持 SSH 和 HTTPS。另两组 WiFi 保存了凭证，但当时不在范围，未在该轮完成连接认证测试。本文不包含 WiFi 密码、SSH 密码或授权密钥。

## 3. 系统结构与文件位置

### 3.1 推荐保留的分层

新项目界面 → 新项目后端适配层 → 树莓派 HTTP 服务 → 串口控制／CSI 图像采集 → 云台与摄像头。

树莓派服务内部：

- `systemd`：负责开机启动和进程异常退出后的重试。

**推荐新项目只替换界面或增加后端适配层，不先重写已验证的硬件控制层。**

## 4. 坐标、反馈与中位

### 4.1 坐标定义

| 参数 | 范围 | 方向与含义 |
|---|---|---|
| X / `x` | −180°～180° | 从摄像头朝向看，正值向右，负值向左 |
| Y / `y` | −30°～90° | 正值向上，负值向下 |
| `dx` / `dy` | 普通单轴步长绝对值不超过30° | 相对当前实测位置的增量 |
| 中位 `home` | 当前为 −55°／4° | 已保存的绝对命令坐标，不是把坐标系重新清零 |

服务先校验角度再四舍五入为整数命令坐标。允许范围是协议范围，不代表整套安装在所有角度都无碰撞、无拉线风险；更窄的机械安全范围应在新项目中另行配置。

### 4.2 三类位置不能混用

- `measured`：舵机反馈的角度，带小数。只有 `feedback.fresh=true` 且无故障时才能用于决策。
- `target`：本次进程最后发送的整数目标，含 `verified` 到位标识；不是持续更新的实测值，重启后为空。
- `home`：持久化的中位目标；重启加载，但不自动执行。

`/position` 顶层 `x/y` 是新鲜实测值，不再是旧网页的目标缓存。反馈过期时顶层 `x/y=null`，但 `measured` 可能仍保留历史数据，客户端不得绕过 `fresh` 判断。

### 4.3 到位与保护阈值

- 反馈新鲜度阈值：0.8秒；没有新鲜反馈或有锁存故障时，禁止移动和保存中位。
- 普通 `/move` 和 `/step`：目标与实测的最大轴差限制约30°，比较时有0.6°容差。`/center` 是例外，可一次返回较远的保存位置，不能宣称所有命令都被30°硬限制。
- 移动命令使用 `SPD=30`、`ACC=3`，由固件换算成舵机参数；不是实测的精密恒速保证。
- 到位容差：两轴各1.2°，通过后续反馈序列确认。移动 HTTP 请求会阻塞等待，超时预算为 `max(2秒, 最大轴差/30 + 2秒)`。
- ID 1或2返回 `T1005,status=0` 后故障锁存，后续看似正常的缓存角度不会自动解除故障。排除电源／连接问题后需重启服务。

**安全边界：目前没有经验证的 HTTP 急停或超时自动停止机制。请求失败不表示设备没动或已经停止；移动超时、网络断开或取消等待后，应先读取实际位置并查看画面，不能盲目重复发指令。**

## 5. HTTP API 接入契约

### 5.1 通用请求规则

服务基地址为 `http://100.73.202.93:5000`。GET 不要求控制凭证；所有 POST 同时要求：

1. `Content-Type: application/json`，请求体为 JSON 对象，最大4096字节。
2. `X-Control-Token` 请求头，值来自当前服务进程渲染的首页。
3. 请求携带 `Origin` 时，其主机和端口必须与服务收到的 `Host` 相同。

首页含 `meta[name="control-token"]`。凭证每次服务进程启动重新生成，没有独立获取凭证或刷新凭证的 API。服务端程序可先 GET 首页解析该值；403后重新取页面，但不得自动重放移动指令。

此凭证主要用于防跨站写入，**不是完整的用户身份认证**：能访问首页的人也能获得凭证，GET图片也未做独立鉴权。目前安全边界主要依赖 Tailnet 网络访问限制。新项目应在自己的后端增加鉴权、授权、限流和操作审计，不能把此凭证当永久 API 密钥。

### 5.2 接口总览

| 方法与路径 | 请求体／用途 | 成功返回 |
|---|---|---|
| GET `/` | 控制网页及动态凭证 | HTML |
| GET `/health` | 相机与反馈健康检查 | 健康200，不健康503 |
| GET `/position` | 状态读取 | 状态对象，无 `success` 外层 |
| GET `/snapshot.jpg` | 最新单帧 | `image/jpeg`；画面不可用503 |
| GET `/video_feed` | 实时帧流 | `multipart/x-mixed-replace; boundary=frame` |
| POST `/step` | `{"dx":-5,"dy":0}` | 成功＋实测状态 |
| POST `/move` | `{"x":-55,"y":4}` | 成功＋实测状态 |
| POST `/center` | `{}` | 回到已保存中位并验证 |
| POST `/home/save` | 明确确认、预期实测与版本号 | 保存成功＋最新状态 |

`/health.ok=true` 仅表示相机及反馈正常，不保证已保存中位。需单独检查 `home_saved` 或 `/position.home`。

### 5.3 `/position` 主要字段示例

以下为说明性片段，数值不是当前设备实时读数：

```json
{
  "x": -55.385,
  "y": 4.044,
  "measured": {"x": -55.385, "y": 4.044},
  "feedback": {
    "fresh": true,
    "age_seconds": 0.03,
    "source": "servo_feedback",
    "error": null
  },
  "target": {"x": -55, "y": 4, "verified": true},
  "home": {"schema": 1, "x": -55, "y": 4},
  "home_error": null,
  "revision": 31,
  "busy": false,
  "servo_ids": {"pan": 2, "tilt": 1}
}
```

真实 `home` 还包含保存时实测值、保存时间和来源；响应还包含 `limits`、`max_move_degrees`。`revision` 是进程内计数，移动发送或中位保存后增加，服务重启会重置，不能当跨重启全局版本号。

移动成功外层为 `{"success":true,"verified":true,"state":...}`。响应内 `state.busy` 可能仍为 true，因为状态在释放操作锁之前生成；动作完成后再 GET `/position` 获取空闲状态，不能只据该快照判断服务一直忙碌。

### 5.4 保存中位的正确步骤

1. 用户通过画面将相机调到认可的正前方，停稳。
2. GET `/position`，确认 `feedback.fresh=true`、无故障、`busy=false`。
3. 显示该实测位置，请用户明确确认。
4. 使用本次读取的实测值与 `revision` 发 POST；不是把示例数字写死。

```json
{
  "confirm": true,
  "expected": {"x": -55.209, "y": 4.132},
  "revision": 29
}
```

这里的数字仅演示字段格式。服务会检查版本一致、预期位置偏差不超过1.2°、最近0.7秒内至少3个反馈样本且时间跨度至少0.15秒、两轴波动均不超过0.8°。不满足时拒绝保存，避免把运动中或其他操作后的视角误存为中位。

### 5.5 错误处理

| HTTP状态 | 典型原因 | 新项目处理方式 |
|---|---|---|
| 400 | 非数字／布尔／非有限数、越界、过大移动、错误请求体 | 修正输入，不能原样重试 |
| 403 | 动态凭证失效或跨站来源不匹配 | 更新凭证或修正代理；不自动重放动作 |
| 409 | 另一个动作未完成、未保存中位、位置不稳、版本冲突 | 读取最新状态后让用户重试 |
| 500 | 中位文件写盘失败 | 检查权限和磁盘；不能提示已保存 |
| 502 | 已发出移动但未在预算内验证到位 | 停止追加动作，检查实测、画面及机械状态 |
| 503 | 无新鲜反馈、串口或舵机故障、摄像头不可用 | 检查硬件与进程；禁止盲目发送移动 |

控制类错误通常为 `{"success":false,"error":"原因","state":...}`；图片接口错误可能只有 `error`。客户端应先检查状态码和内容类型，不要把错误 JSON 当 JPEG 解码。超出请求体大小等框架错误不保证遵循同一 JSON 结构。

## 6. 如何整合到另一个项目

### 6.1 推荐方案：新项目后端做适配层

保留现有硬件服务，新增一个轻量适配模块负责：

1. 将设备基地址做成配置项，服务端先确认 Tailnet 路由可达；普通公网云服务器不会天然连通该私网地址。
2. GET 首页提取当前 `X-Control-Token`，只在后端内存保存；服务重启或403后重新获取。
3. 先检查 `/health` 和 `/position`，再接受人工移动意图。
4. 按设备串行发送移动操作；409时不形成无限重试队列。相对动作直接用 `/step`，不要用浏览器的旧缓存自己叠加角度。
5. 将 JPEG 和 MJPEG 按需转发给新项目；对流式响应关闭代理缓冲，配置合理的连接超时与并发限制。
6. 在新项目做身份权限、用户确认、访问日志及断连提示，不能让模型随意保存中位或执行硬件校准。

可设计 `get_status`、`get_snapshot`、`move_relative`、`move_absolute`、`go_home`、`save_home` 六个适配函数；这是建议的新项目接口，不是设备当前已有的函数导出协议。

当前写请求会拒绝不匹配的浏览器 `Origin`，没有启用 CORS，且响应设置 `X-Frame-Options: DENY`。因此：

- 不要直接把整个控制网页放进新项目 iframe。
- 不要假定新域名页面可以直接跨域 POST。
- HTTPS 页面直接加载 HTTP 私网图片可能被浏览器混合内容策略阻止。
- 推荐由新项目后端统一代理画面和控制。代理向设备发起请求时，避免转发不匹配的浏览器 Origin，并在新项目自身完成权限与防跨站校验。

### 6.2 最小接入调用顺序

```text
读取首页 → 解析动态控制凭证
读取 /health 和 /position → 展示实测状态
用户点击“向左5°” → POST /step {dx:-5,dy:0}
检查 success / verified → 再 GET /position
用户点击“归中” → POST /center {}
需要改中位 → 单独确认后 POST /home/save
```

客户端应为控制请求设置约20秒上限，以覆盖当前全范围归中等待。超时不等于未执行，不可直接重放 `/step`；先读状态判断设备到了哪里。

### 6.3 只读 Python 示例

以下只读示例可用于适配层连通性检查，不获取凭证、不发送移动：

```python
import json
from urllib.request import urlopen

BASE = "http://100.73.202.93:5000"
with urlopen(BASE + "/position", timeout=3) as response:
    state = json.load(response)

if not state["feedback"]["fresh"]:
    raise RuntimeError("没有有效舵机反馈，禁止控制")

print("实测：", state["measured"])
print("中位：", state["home"])
```

调用 POST 时需按第5章先取得凭证并补齐请求头。初次验收建议只做1°～5°微调，不用极限位置或最快速度试运行。

### 6.4 必须合并到新进程时

只有确实需要重构时才采用这一方案：先备份程序和中位，在维护窗口停止原服务，确保原进程释放串口与相机，再将 `Controller`、`Camera` 和 API 生命周期完整迁入新应用。新应用仍只能有一个硬件工作进程。

现版本不能直接换成多进程 WSGI worker：每个进程会竞争硬件、生成不同控制凭证，并持有不一致的内存状态。也不能直接用导入 Flask 应用的通用启动命令替代当前脚本，因为相机和控制器是在 `main()` 中初始化。若要改服务框架，需要设计单硬件进程或独立硬件守护服务，并重新验收；这些改造当前尚未实施。

## 7. 中位文件、串口协议与安全边界

### 7.1 中位文件样例

```json
{
  "schema": 1,
  "x": -55,
  "y": 4,
  "measured": {"x": -55.209, "y": 4.132},
  "saved_at": "2026-10-20T14:32:21+00:00",
  "source": "servo_feedback"
}
```

`x/y` 是归中使用的整数目标；`measured` 是保存时的参考实测；时间为 UTC 格式。写入采用临时文件、文件同步、原子替换和目录同步，目录权限0700，文件0600，运行用户 `chs` 可写。

原机软件迁移应原样保留此文件；换相机安装角度、拆装机械或换整套设备时，不应盲目复制这一坐标，应重新人工确认并保存。文件缺失或损坏时禁止归中，不默认为 `(0,0)`。

### 7.2 已验证串口消息

正常业务优先使用 HTTP。下列消息用于理解底层，不意味着允许另一程序与运行服务抢开串口。

| 类型 | 示例 | 说明 |
|---|---|---|
| 绝对角度控制 | `{"T":133,"X":-55,"Y":4,"SPD":30,"ACC":3}` | 水平ID2、俯仰ID1由固件决定，命令没有轴ID参数 |
| 开启云台模块反馈 | `{"T":4,"cmd":2}` | 易失运行设置，不改舵机EEPROM |
| 开启诊断输出 | `{"T":605,"cmd":1}` | 用于接收舵机错误消息 |
| 开启连续基础反馈 | `{"T":131,"cmd":1}` | 配合云台模式输出角度 |
| 请求基础反馈 | `{"T":130}` | 返回基础信息；字段取决于模块模式 |
| 关闭自稳 | `{"T":137,"s":0,"y":0}` | 防止自稳循环干预人工控制 |
| 舵机反馈 | `{"T":1001,"pan":-55.385,"tilt":4.044}` | 示例省略其他IMU／电压字段 |
| 舵机通信失败 | `{"T":1005,"id":2,"status":0}` | 故障锁存并禁止后续控制 |

应用启动按“关自稳 → 诊断输出 → 云台模块 → 连续反馈 → 请求反馈”配置运行态，不发送移动、归中、扭矩解锁、改ID或中位校准。此承诺针对应用；ESP32自身上电时的固件行为仍需单独断电测试。

`T501`改ID、`T502`硬件中位校准、`T210`扭矩控制不属于正常接入流程。不得在启动代码或归中逻辑中调用。旧普通 PWM 字符串协议不适用这块 ESP32 控制板。

### 7.3 为什么必须监听错误

官方固件在舵机反馈失败时可能保留旧的内部位置缓存。因此不能只看后续 `T1001` 仍有数字就认定恢复；现服务监听 ID 1／2 的 `T1005` 并锁存错误。新项目若重写硬件层，必须保留这一保护及0.8秒反馈新鲜度判断。

## 8. 开机自启、维护与迁移步骤

### 8.1 当前自启服务

- 服务名：`pantilt-web.service`，已执行 `enable`，最后核验为 enabled／active／running。
- 启动命令：`/usr/bin/python3 /home/chs/pantilt_web/pantilt_web_server.py`。
- 工作目录：`/home/chs/pantilt_web`；用户与组均为 `chs`。
- 环境变量：`PANTILT_HOST=100.73.202.93`、`PANTILT_SERIAL=/dev/serial0`。
- HTTP端口5000在当前代码中固定；中位路径由脚本所在目录加 `state/home.json` 得到，尚未做成环境变量。
- 排序在 `network-online.target`、`tailscaled.service` 之后；异常退出按 `Restart=on-failure`、`RestartSec=5` 重试。
- 启用 `NoNewPrivileges=true`、`PrivateTmp=true`、`ProtectSystem=full`、`ProtectHome=read-only`，仅通过 `ReadWritePaths` 给中位目录写权限。

网络启动排序不等于 Tailnet 地址一定就绪；地址延迟可导致绑定失败后进程重试。`Restart=on-failure` 也不是健康监控：相机初始化失败但进程仍存活、舵机故障锁存或只有 `/health=503` 时，不保证自动恢复。现版本未增加健康看门狗或相机自动重连。

### 8.2 常用维护命令

只读检查：

```bash
systemctl is-enabled pantilt-web.service
systemctl status pantilt-web.service --no-pager
python3 /home/chs/pantilt_web/diagnose.py
journalctl -u pantilt-web.service --since "30 minutes ago" --no-pager -n 100
```

设备确认空闲、硬件供电正常后，才在维护窗口执行：

```bash
sudo systemctl restart pantilt-web.service
```

重启会中断视频连接、改变动态控制凭证、清空本次目标／计数及故障锁存，但中位文件应保留。它不是急停，也不自动归中。维护后须重新读取 `/health` 和 `/position`。

### 8.3 新项目接入／迁移清单

1. **先选方式。** 能通过 HTTP 复用就不动设备服务；只有合并硬件进程或换主机时才停止原服务。
2. **先备份。** 保存第3章五项文件，并记录系统版本、依赖版本、GPIO／相机状态；不把网络凭证或 SSH 密钥混入代码包。
3. **确认设备所有权。** 无第二个摄像头或串口进程；保留其他业务服务，不广泛终止 Python 进程。
4. **准备相机系统栈。** 确认 Raspberry Pi 平台与 Picamera2、libcamera、pyserial、Flask 可用；虚拟环境需能使用系统相机包。
5. **调整地址和权限。** 换主机后更新 Tailnet IP、运行用户、串口设备、服务工作目录和中位目录写权限，不可照抄旧用户名与IP。
6. **保留启动语义。** 单进程硬件所有者，先关闭自稳再启反馈，不自动运动，不进行任何EEPROM校准。
7. **按第9章验收。** 先只读，再小幅动作，最后用户确认中位。启用自启后，另做经过确认的整机及控制板断电测试。
8. **最后再切换。** 新路径验证通过后才停用旧接入；保留可恢复的原文件与服务配置，避免同时运行两个硬件进程。
